# Directional running and hover

Ground movement uses GASP's existing eight-way run motion matching. Backward and side inputs keep the character facing the view, including while the camera turns. The existing starts, stops, shuffle steps, diagonal transitions and natural shoulder/hip motion remain. Sprint is retained for forward travel; requesting backward/side movement ends forward sprint. No GASP animation asset was modified or retargeted.

`RPGGASPInputBridgeComponent::bDirectionalGroundMovement` controls the new ground routing. The adapter supplies WantsToStrafe during movement and briefly through the stop. The actual backward run selection is verified from the live motion-matching node; the asset audit also confirms that backward loop, start and stop clips are already referenced by the original databases.

Hover has its own four-direction airborne pose layer. It samples the approved upright hover base and blends view-relative forward/back and left/right poses, including diagonals. The pelvis leans gently into travel, the spine balances the lean, and arms/legs trail and brace. The same direction-and-speed logic used for grounded locomotion drives these poses; it never plays a grounded running cycle in the air. Animation-side smoothing handles acceleration, stopping, reversal and return to idle. Rejected physics-based flight follow-through stays disabled.

From hover, backward, sideways and diagonal inputs remain upright and view-facing. Light forward stick input stays in hover. Full forward input (more than 65% action magnitude, within the forward cone) enters the existing travel flight; from backward/side motion it first finishes the reversal. Charging a spell also keeps forward movement in hover. Release movement to settle out of travel flight before choosing a new hover direction. Normal/fast forward flight and explicit hold-A rise keep their existing presentation and settings. Keyboard movement remains on the existing GASP actions; a held spell supports forward hover with full keyboard input.

`RPGDirectionalHoverComponent` is auto-added by the existing controller helper. Hover speed defaults to 320 cm/s. A temporary pre-movement MaxFlySpeed cap applies only during directional hover; it restores the original value on exit, landing and fast-flight toggle. The original ground acceleration/flight ownership order is preserved. The post-movement velocity limit is only a safety clamp. Backward/side hover does not inherit travel flight's look-pitch climb/dive coupling, so aiming upward does not unintentionally change hover height. Spells can charge/fire while moving in this hover state.

Idle hover has a subtle visual bob: 1.6 cm amplitude, 3.4-second period (about 3.2 cm peak to peak). It activates only with negligible velocity and no movement input, fades out in motion and eases back in after stopping. Only the evaluated body pose moves; the capsule stays at the same height. The first-person shadow copies the same hover snapshot. Bob does not run on the ground or during travel flight.

Tuning: HoverSpeed, PoseResponse, IdleBobAmplitude and IdleBobPeriod on RPGDirectionalHoverComponent. Third-person framing, palms, recoil, damage, impacts and punch controls are retained. The final pose is applied after the flight layer and before spell aiming; a zero hover weight leaves the existing travel pose path unchanged.

Review tools: `Tools/GASP/check_directional_assets.py` reads asset references; `Tools/GASP/review_directional.ps1` runs `RPG.Movement.Directional` or `Visual.DirectionalMovement` in a disposable PIE world. It uses real Enhanced Input, movement physics, GASP selection and the actual player camera, creates temporary floor fixtures and never saves a level. Results/captures are under Saved/DirectionalReview; logs under Saved/Logs/Directional-*. See Saved/DirectionalMovement_Status.md for accepted tests and the current checkpoint. A full packaged build and the broad historical combat suite are outside this pass.
